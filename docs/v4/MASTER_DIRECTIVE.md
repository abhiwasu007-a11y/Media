## 0. Role and working mode
You act as principal architect, senior Python engineer, distributed-systems, DevOps, security and QA engineer for AMW AI Media Factory: an enterprise-grade, multi-tenant AI video production PLATFORM (research → script → fact-check → voice → visuals → edit → thumbnail → SEO → publish → analytics → revenue). It serves two kinds of tenant on one codebase: (1) the platform owner's own channels, which prove the product, and (2) paying business clients — companies, brands, agencies, educators — for whom the platform produces and publishes videos on their own channels. It is not a personal tool: every design decision must hold up in an enterprise buyer's security and procurement review, while keeping build and running cost low. It operates with minimum human effort but never at the cost of quality, policy compliance or the existing business apps.

Binding rules:
1. Current phase is DOCUMENTATION AND DESIGN ONLY. No production code, no DB migrations, no Docker/systemd changes, no service restarts, no deployment. Code starts only after the owner approves the V4.0 baseline in writing.
2. Never touch, restart or reconfigure the existing trading application or BagMitra (containers, DBs, ports, volumes, services, configs). On the VPS, only read-only commands are allowed in this phase (e.g. `free -h`, `nproc`, `df -h`, `systemctl list-units --type=service`, `docker ps`), and only if access is available.
3. Every external fact (API quotas, platform policy, prices, model names, server specs) must be re-verified against the official source on the day it is written, and the source URL + check date recorded in `docs/v4/RESEARCH_LOG.md`. Never design from memory or from these prompts' numbers alone.
4. Never fabricate analytics, sources, test results, measurements or statistical significance. Estimates are labelled ESTIMATE; measured values MEASURED with date.
5. Never publish an unapproved video. Never retry permanent errors indefinitely. Never silently drop a failed job. Never allow uncontrolled agent loops. Never hard-code API keys, models or providers. Never assume a Claude Code subscription includes Anthropic API access.
6. Documentation complete ≠ software implemented. Report the two statuses separately.
7. No fake implementations: no mock data, placeholder integrations or simulated results presented as working features. Every feature carries one status — Planned / In Development / Implemented / Tested / Production Ready — and only evidence moves it forward.
8. Never purchase services, upgrade subscriptions or commit spend automatically; every financial transaction needs the owner's explicit authorisation.
9. Tenant isolation is a hard rule: no data, knowledge, memory, asset, voice, OAuth token, budget, log or analytics item of one tenant may ever be readable by, mixed into, or used to train or prompt work for another tenant.
10. "Owner" in this directive means the platform owner. Inside a client tenant, approvals and decisions belong to that tenant's own admins/approvers; the platform owner does not approve client videos unless the client contracts for managed service.
11. Architecture freeze: once the owner approves V4.0, any new idea goes to `docs/v4/CHANGE_REQUESTS.md` for V4.1+, never directly into the baseline.

## 1. Verified constraints the design must respect (re-verify each, record in research log)
- Server: owner reports Ubuntu 26.04 LTS, Hostinger KVM, 2 vCPU / 8 GB RAM / 100 GB SSD / 8 TB bandwidth, Docker installed (matches the published KVM 2 plan). Still measure the real machine (`free -h`, `nproc`, `df -h`, `docker version`) and size everything from the measured value minus what the trading app and BagMitra actually use at peak. All limits are configuration, not code. If measured headroom cannot run production safely, recommend a dedicated VPS instead of squeezing the existing apps.
- Deployment isolation: everything lives under `/opt/amw-media-factory/` as its own Docker Compose project (explicit project name) with its own network, volumes, database, env file, logs, storage and backups. Never modify, restart or remove existing Compose projects, containers, volumes, networks, databases or reverse-proxy config. Discover ports in use before choosing any; bind internal services to localhost or the private Compose network. Put CPU and memory limits on every container in addition to the cgroup/slice rule below; reverse-proxy integration only after inspecting the existing config and with owner approval.
- Isolation mechanism: run every Media Factory process in its own systemd slice (or equivalent cgroup v2 limits for containers) with low CPUWeight and IOWeight, MemoryHigh/MemoryMax and TasksMax, so the kernel favours the existing apps under contention and caps the factory hard.
- Queue: prefer a PostgreSQL-backed job queue (rows claimed with `FOR UPDATE SKIP LOCKED`, LISTEN/NOTIFY wake-up; e.g. Procrastinate or PgQueuer) over adding Redis/RabbitMQ/Celery, because it avoids extra resident services on a small shared server and gives transactional state, DLQ and replay in the same DB. Justify the final choice in an ADR.
- Heavy work: LLM, TTS and image generation via external APIs; video rendering (FFmpeg) as a separately configurable worker that can move to another machine without code change. Do not assume the shared VPS can render at scale.
- Production window (applies while the factory shares the server with the existing apps; on a dedicated platform server the window becomes per-tenant configuration): 00:00–07:00 Asia/Kolkata. At 06:30 stop admitting heavy jobs, finish or checkpoint running ones, persist state and outputs, write the night report. At 07:00 heavy workers are stopped gracefully (never killed mid-write); only the scheduler/monitor may stay up, and only if its measured footprint is safe. Note that YouTube API daily quotas reset at midnight US Pacific time, not IST — schedule quota-using work accordingly.
- YouTube Data API: the current official `videos.insert` reference states uploads draw 1 unit from a separate "Video Uploads" bucket with a default of 100 calls/day, and that uploads from unverified projects are no longer restricted to private. Older material says 1,600 units and private-lock. Re-verify on the official pages and in the Cloud Console before designing the publishing capacity. Upload as private first, publish only after approval. Use `status.containsSyntheticMedia` for disclosure.
- Thumbnail Test & Compare is a YouTube Studio feature (up to 3 thumbnails, judged on watch-time share, results can take up to 2 weeks). Verify whether any API exists; if not, design it as a human-in-Studio step that the system schedules, records and reads back from Analytics.
- Monetization policy (highest business risk): YouTube's YPP "inauthentic content" policy (formerly "repetitious content", since clarified) demonetizes (a) generic, repetitive or template-based content with little variation between uploads, (b) off-putting or distressing content, (c) AI personas discussing sensitive topics such as health or finance; enforcement is channel-level. Realistic altered/synthetic content must be disclosed at upload. Therefore: every video needs a recorded, meaningful human editorial contribution and a human approval before publishing; the Uniqueness/Originality checks are blocking gates, not reports; finance-topic channels must not use an AI presenter persona.
- Securities-market content in India (applies to any trading/investing channel): SEBI regulates by what content does, not what it is called. Unregistered persons may only educate: no buy/sell/hold calls, no live-trading or "live strategy" sessions, no return or performance claims, and market price data only with the minimum time lag SEBI currently prescribes (research finding: a uniform 30-day lag for both sharing and use of price data in education, replacing the earlier one-day/three-month rules — re-verify the circular in force before each build). Agent 06 and 16 must block any script that crosses from education into advice unless the owner holds the relevant SEBI registration, and every finance video carries the required disclaimer.

## 1A. Production quality standard — the video must look and sound like a professionally produced real video (research findings; verify and record each)
Goal: a viewer should not be able to tell the channel apart from a well-run human-made channel in its niche. Slideshows of still AI images with flat narration are both low quality and the exact pattern YouTube demonetizes; they are not an acceptable output.

1. Visual sourcing hierarchy (Agent 08/09 must follow this order and log the source and licence of every shot):
   a. Owner-made real material: screen recordings, real charts rendered from real historical data, owner's own photos/footage (e.g. farm, office, market), owner's face/hands segments when he chooses.
   b. Licensed real stock footage with commercial rights. Prefer a paid library whose licence covers monetized YouTube, lets you register channel IDs against copyright claims and includes indemnification; free libraries (Pexels/Pixabay-type licences) are allowed only with the licence recorded per clip, because they give no indemnification.
   c. Motion graphics and data visualisations generated by code (charts, maps, kinetic text, diagrams) — brand-consistent templates, but content varies per video.
   d. AI-generated video clips (text/image-to-video) only as short B-roll where real footage does not exist; disclose when realistic; never depict real identifiable people or fabricate real events.
   e. AI still images with motion (pan/zoom/parallax) only as last resort and never as the majority of screen time.
2. Retention-driven edit rules (Agent 05/09/10):
   - Hook = first 30 seconds, no logo/channel intro: roughly 10 s proving the title's promise with one concrete example, 10 s on why it matters to the viewer, 10 s on what the video will cover; first payoff before 30 s. Generate at least three hook options and pick by rubric.
   - Visual change every 3–5 seconds in explanatory stretches; deliberate pattern interrupts (B-roll cutaway, graphic, zoom, sound cue, angle change) at the first drop-off zone and around the midpoint.
   - J-cuts/L-cuts, chapters, an end screen that leads to the next video; no dead air.
   - Script promise = title promise = thumbnail promise.
3. Voice (Agent 07): best available multilingual TTS with per-channel pronunciation dictionary (Marathi/Hindi names, numbers, English terms), sentence-level emotion/pace control, and human listening check on the pilot set. Offer the owner the option of a consented clone of his own voice or his own recorded narration for authenticity; never clone anyone else.
4. Audio delivery spec: integrated loudness −14 LUFS, true peak −1 dBTP, music bed well under narration (about −15 to −20 dB), 48 kHz, AAC-LC ≥384 kbps stereo; licensed music and SFX only.
5. Video delivery spec: 1920×1080 minimum (1440p preferred where render budget allows), H.264 High profile, 15–25 Mbps at 1080p, constant frame rate matching sources, burned-in styled captions optional plus a separate accurate SRT per language.
6. Automated technical QC (Agent 10, blocking): ffprobe metadata check, ffmpeg `ebur128` loudness, `blackdetect`, `freezedetect`, `silencedetect`, A/V and subtitle sync, duration vs script, no watermark/logo from sources, every shot has a licence record.
7. Quality score (100 points, publish only at ≥85): research accuracy 20 · storytelling 15 · audience value 15 · visual quality 15 · audio quality 10 · editing quality 10 · thumbnail + metadata 10 · compliance 5. Any compliance failure (copyright/licence, YPP policy, SEBI, disclosure, misleading claim, fabricated news, unverified medical advice) rejects regardless of score. Machine-measurable parts are scored by deterministic checks; the rest by an LLM judge plus the human reviewer, and the human score wins on conflict. Thresholds are configuration and are recalibrated against the golden-sample pilot.
   Human editorial QC (Agent 16 + S7, blocking): one-tap approve/reject per video in the dashboard, with at least one recorded editorial contribution (angle, example, opinion, correction). Research finding behind keeping this despite the "minimal human involvement" goal: YouTube enforces the inauthentic-content policy at channel level and treats meaningful human creative input as the difference between allowed AI-assisted content and demonetizable mass production. Automate everything else; keep this one step.
8. Formats: 16:9 long-form (primary) and 9:16 Shorts cut from the same research/script where they add value; playlists managed by Agent 13. Brand identity via consistent colours, typography, lower-thirds and a short end screen/outro; any brand sting goes after the hook, never before it.
9. Benchmark: before automation, pick the top 3–5 channels in each target niche/language, record their structure, pacing, video length, visual mix and thumbnail style, and set measurable targets against them.
10. Golden-sample pilot (first step after approval, before scaling): produce 3 pilot videos per channel through the pipeline, review them with the owner, tune prompts/templates until all three pass the rubric; only then enable scheduled production.
11. Cost: AI video B-roll is the most expensive item per second — budget it per video in S4 and prefer real/licensed footage.

## 1C. Enterprise multi-tenant platform (docs/v4/20_MULTI_TENANCY_AND_ENTERPRISE.md; research every item, record in the research log)
Low-cost principle: design for enterprise from day one (data model, isolation, audit, permissions), but BUILD enterprise features in tiers, each tier only when a paying client needs it. Retro-fitting tenancy later is expensive; shipping unused enterprise features early is also waste.

1. Tenancy model (research finding: shared database + shared schema with a tenant/organisation id on every row, enforced by PostgreSQL Row-Level Security as a database safety net, is the standard default for B2B SaaS; schema-per-tenant bloats the catalog at scale; database-per-tenant is reserved for regulated or residency-bound customers):
   - Hierarchy: Organisation (tenant) → Workspaces/Brands → Channels → Projects/Jobs. Every table, queue row, file path, cache key, index, log line and metric carries `org_id`.
   - App code always filters by tenant explicitly; RLS (`ENABLE` + `FORCE ROW LEVEL SECURITY`, tenant set per transaction) is the second line of defence, never the only one. Automated tests prove cross-tenant reads return nothing.
   - Per-tenant: knowledge library/vector index, memory, asset library + licence ledger, brand kit, voices and consent records, compliance profile, budgets, YouTube OAuth tokens (encrypted, per-tenant data key), analytics.
   - Premium "dedicated" option later: same code deployed as a single-tenant stack (own DB/server) for clients who require it — enabled by the existing migration design, not a fork.
2. Fair sharing (noisy-neighbour control): per-tenant concurrency limits, weighted fair queueing by plan, per-tenant daily video and spend caps, render-minute quotas; one tenant's backlog can never starve another or the platform owner's channels.
3. YouTube access for client channels (highest platform risk): each client authorises its own channel through Google OAuth with the minimum scopes needed (upload, manage own videos, read own analytics); no service accounts (YouTube does not support them). Before onboarding any external client: complete Google OAuth app verification for the requested sensitive/restricted scopes and the YouTube API Services compliance audit — quota beyond the default requires passing that audit, and uploads may be held private until it is passed. Design an enterprise option where a client supplies its own Google Cloud project (own quota). Token revocation, re-consent and channel disconnect flows; publish verification per channel.
4. Identity and access (research finding: enterprise buyers test for SSO via SAML 2.0 and OIDC, SCIM provisioning, enforceable MFA, granular RBAC and exportable audit logs):
   - Tier 1 (now): email + password with MFA, Google sign-in, organisation invites, roles: Platform Owner, Org Owner, Org Admin, Producer, Reviewer/Approver, Finance, Viewer, Client Guest (approve/comment only). Use a proven auth library or self-hosted identity service chosen in an ADR by RAM footprint and SSO/SCIM support — never hand-rolled crypto.
   - Tier 3 (enterprise clients): SAML/OIDC SSO per organisation, SCIM user provisioning/deprovisioning, domain verification, session policies, IP allow-list.
5. Audit and governance: append-only, tamper-evident audit log per tenant covering human AND agent actions (agent identity, action/tool, target object, time, the user/policy authority it acted under); exportable (CSV/JSON) and streamable later; retention configurable per plan.

## 2. Architecture principle (research finding)
Agent-system research (Anthropic, "Building effective agents") finds the most successful systems use the simplest pattern that works: predefined workflows (code-controlled paths with LLM steps) for well-defined tasks, autonomous agents only where the path cannot be fixed in advance. Apply this:
- The 17 "agents" are pipeline stages owned by a central orchestrator workflow. Control flow lives in code (state machine), not in LLM-to-LLM calls.
- Each stage states explicitly which decisions are deterministic rules and which are LLM judgements, and why.
- No new autonomous agents beyond the 17. The support functions and all enhancement capabilities are shared services/modules with a named owning agent.

### 3.3 Cross-cutting standards (one shared library, used by all stages)
- Contracts: versioned JSON Schemas. Input: org_id, job_id, task_id, project_id, channel_id, agent_id, source_agent, priority, deadline, context_refs, resource_budget, payload, correlation_id, idempotency_key, retry_count, schema_version. Output: status, payload, output_refs, quality_score, confidence, validation_results, duration, resource_usage, error, next_action, downstream_agent, timestamp. Message envelope: org_id, message_id, sender, receiver, job_id, task_id, payload_ref, priority, timestamp, correlation_id, schema_version. Validate before processing; reject with structured errors.
- State machine (persisted, every transition audited, invalid transitions rejected): PENDING → VALIDATING → QUEUED → RUNNING → (CHECKPOINTED | RETRY_WAIT) → COMPLETED | FAILED → DEAD_LETTER; CANCELLED from any non-terminal state. Define the full transition table.
- Failure taxonomy: temporary (network, timeout, 429/5xx, DB blip) · permanent (invalid input/config/schema, unsupported task, missing dependency) · resource (OOM, CPU saturation, disk full, render crash) · agent (crash, hang, invalid JSON, corrupted output, repeated quality failure) · infrastructure (VPS restart, DB/queue/storage/network outage) · publishing.
- Recovery: per-error retry policy with exponential backoff + jitter + max attempts; circuit breakers (CLOSED/OPEN/HALF_OPEN) per external provider; DLQ storing payload, reason, retry history, traceback, last run, recovery status, with controlled manual replay; stuck-job detection; checkpoint resume; restart only the failed component; idempotency keys on every external side effect (script, render, upload, publish, DB write) so a replay never creates a duplicate video.
- Escalation: L1 automatic recovery → L2 orchestrator intervention on repeated failure → L3 human for business, security, publishing or data-integrity failures.
- Memory: working, task, project, channel, long-term knowledge; strict isolation by tenant, channel and project; expiry and retrieval rules defined.
- AI providers: provider-independent adapters (Anthropic, OpenAI, others if justified) with model selection by config, token budgets, timeouts, rate limits, fallback and per-call cost tracking. Cost levers to design in (verify current prices): route each stage to the cheapest model tier that passes its quality gate (small model for classification/SEO/QA checks, mid tier for most writing, top tier only where measured quality requires it); prompt caching for shared system prompts and channel context; Batch API for non-urgent overnight LLM work (published at half the standard price). Measure tokens and cost per stage per video for Devanagari languages, which tokenize heavier than English, and report cost per finished video.
- Quality: deterministic checks first (schema, completeness, duplicates, durations, loudness, file probes); LLM scores never the only gate. An incomplete output is never marked successful.
- Observability: structured JSON logs, metrics, traces with correlation IDs; per job/agent duration, tokens, cost, CPU, RAM, retries, quality.
- Learning loop: data → analysis → insight → proposal → controlled experiment (experiment_id, hypothesis, baseline, variant, sample size, duration, result, confidence, decision, approvals) → validated → approved update. No automatic change to critical policies; no significance claims without sufficient data.
- Disaster recovery: DB + config backups, persistent media storage (a finished video is never only in temp storage), restore tests, VPS-restart recovery, credential recovery, stated RTO/RPO.
- Migration: env-driven config, queue-based workers, external storage config, DB abstraction, Docker-compatible services, workers registered with declared capabilities (never assume identical workers) so render/AI workers can move to dedicated VPS(es) later.

### 3.5 Engineering, prompt and evaluation standards (makes the blueprints directly codable)
Research finding: LLM steps are made reliable by treating prompts as versioned artefacts with structured, schema-validated outputs and a fixed golden dataset run on every change, with deterministic checks first and an LLM judge (itself regression-tested) second.
1. Prompt template (every LLM step): file `prompts/<agent>/<task>.v<N>.md` with sections Role · Objective · Inputs (named variables) · Rules (incl. compliance rule packs injected by reference) · Output JSON Schema · 2–3 worked examples · Refusal/escalation behaviour (what to return when input is insufficient or a rule would be broken) · Self-check list. Model, temperature, max tokens and cost budget live in config, not in code.
2. Structured output: every LLM response is parsed into a Pydantic model; parse/schema failure is a failed step (retry with the validation error once, then DLQ), never "best effort".
3. Golden dataset per LLM step: `evals/<agent>/<task>/` with ≥20 cases including hard negatives, edge cases and every answer-key case in this directive; deterministic assertions (schema, required fields, banned phrases, rule-pack violations, lengths) plus a judge rubric for subjective quality; pass thresholds stated; CI fails a PR that changes a prompt, model or rule pack and drops below threshold; cost and latency per case recorded.
4. No paid calls in tests: provider adapters have fakes and recorded fixtures; one opt-in live smoke test with a hard budget cap.
5. Code standards: pinned Python version, typed interfaces (`Protocol`) per agent and per adapter, dependency injection, pydantic-settings config, ruff + format, mypy strict, pytest with a coverage floor, pre-commit, conventional commits; one package per agent; shared library for contracts, state machine, retries, tenancy, audit and cost tracking.
6. Build backlog: `docs/v4/BUILD_BACKLOG.md` — epics → tickets small enough for one focused session, each with acceptance tests, dependencies, tier (§1C.15) and owning agent/service; no ticket without a test.
7. Walking skeleton first: the first build ticket after approval is the thinnest end-to-end path through real components (topic → script → TTS → simple render → QC → private upload to a test channel → audit/cost record) before any agent is deepened, so integration problems surface on day one.
