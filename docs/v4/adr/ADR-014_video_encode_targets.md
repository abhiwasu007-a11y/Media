## 1. Context
- 18 §6 and §7.1 (`qc.video.bitrate`) gated the **measured** average bitrate of the final file: below 8 Mbps FAIL, 8–15 WARN, 15–25 PASS (directive §1A.5 target 15–25 Mbps; INF-10 floor 8 Mbps).
- Dry-run break 8: code-made still graphics encode at about **115 kbps** with x264 average-bitrate control against the 8 Mbps floor. A static picture needs very few bits; x264 cannot (and should not) spend 8 Mbps on it without padding. The dry run lowered the floor by configuration for that run only.
- YouTube (INF-12, fetched 2026-11-19): "Variable bitrate. No bitrate limit is required, though we offer recommended bit rates below for reference". SDR 1080p: **8 Mbps** at 24, 25, 30 fps; **12 Mbps** at 48, 50, 60 fps. These numbers equal the owner's statement in D10: no mismatch.
- YouTube (INF-13): H.264 High Profile, progressive, 2 consecutive B-frames, closed GOP of half the frame rate, CABAC, 4:2:0; MP4 with the moov atom at the front.
- The installed development FFmpeg (6.1.1) has the `ssim` and `psnr` filters and **no `libvmaf`** (only `vmafmotion`, which is not VMAF). Measured locally with `ffmpeg -filters`; not a research-log fact.
- Measured locally on 2026-11-19 (FFmpeg 6.1.1, libx264 core 164, preset `faster`, 1080p, 2 s windows of the packet sizes), one-pass ABR at 8 Mbps: 1080p30 random noise (8 s) **33.6 / 2.1 / 5.1 / 6.6 Mbps** (mean 11.87); with `maxrate` 12 / `bufsize` 16 Mbps **9.3 / 8.5 / 8.2 / 8.1** (mean 8.52; SSIM All 0.4347 vs 0.4102 without the cap); two-pass (same settings) **25.5 / 1.0 / 4.6 / 3.7** (mean 8.70; SSIM 0.3841). 1080p60 noise (6 s) at 12 Mbps: ABR 26.5 / 9.8 / 10.7 (mean 15.67), with 18 / 24 Mbps 13.8 / 12.2 / 12.1 (mean 12.72). testsrc2 1080p30: 8.16 Mbps with or without the cap; a still graphic: 0.15 Mbps with or without the cap (no padding). The PR #79 review measured the same burst-then-starve on a 20 s noise clip (32.4 Mbps then 2.2 Mbps, recovery about 10 s). Every segment restarts the rate controller, so the burst repeats at every segment start.
- Measured locally: a plain MP4 mux writes an edit list (`elst`) because of the B-frame composition delay; `-use_editlist 0` alone starts the video 2 frames late (0.0667 s at 30 fps); `-use_editlist 0 -movflags +negative_cts_offsets` starts it at 0 with no `elst`. Without an edit list the native AAC encoder's 1024 priming samples (21.3 ms) are no longer hidden: a click at 500 ms decoded at 521.75 ms; dropping 1024 samples from the start of the master puts it at 500.42 ms and makes the audio duration equal the video.
- Measured (PR #79 review, confirmed locally): the ssim filter pairs frames by timestamp; the FFV1 Matroska reference has a 1 ms timebase, so a 30-frame clip gave 31 pairs with one wrong pairing (All 0.997619 vs 0.997806 when aligned). Re-timing both inputs by frame index (`setpts=N/FRAME_RATE/TB`) gives exactly one pair per frame, and the per-frame values equal an independent computation on raw frames.
- Measured locally (FFmpeg 6.1.1, libx264 core 164): the x264 SEI (`x264 - core … options: … rc=abr … bitrate=8000 …`) stays in the stream with `-map_metadata -1` and `+bitexact`; with `-maxrate` equal to `-b:v` x264 reports `rc=cbr`; without VBV it reports `rc=abr` and no `filler` key; `-preset ultrafast` gives Constrained Baseline.

## 2. Options considered
| Option | What it means | Verdict |
|---|---|---|
| A. Floor on the measured bitrate (status quo) | FAIL when the measured average is below 8 Mbps | **Rejected.** YouTube states no bitrate limit is required (INF-12); static content fails for no quality reason (break 8) |
| B. CBR at the target | `-minrate = -maxrate = -b:v`, `nal-hrd=cbr` | **Rejected.** Not what YouTube asks ("Variable bitrate"); wastes bits on simple frames; needs filler to hold the rate |
| C. Filler padding | write filler NAL units until the measured rate reaches the floor | **Rejected (owner D10: no filler padding).** Bytes without picture information; bigger upload, no quality gain |
| D. Encoder target + settings check + quality metric (**chosen**) | encode H.264 High VBR (x264 ABR) at YouTube's target; verify the settings in the delivered stream; measure SSIM against a lossless intermediate | **Chosen (D10).** The target is a sourced fact; the check verifies what can be verified; the metric measures quality instead of bits |

## 3. Decision
1. **Target, not floor.** The delivery encode runs x264 average-bitrate rate control (`rc=abr`, variable bitrate) with `-b:v` equal to the target of `data/encode_targets.json`, keyed by the output size and the exact frame rate. Rows (from INF-12, adopted by D10): 1920×1080 at 24/25/30 fps → 8 000 000 bps; 1920×1080 at 48/50/60 fps → 12 000 000 bps. A configured `agent_10.render.video_bitrate_bps` that differs from a row is refused (`CONFIG_INVALID`, `ENCODE_TARGET_CONFLICT`).
2. **REQUIRES REVIEW (Phase 1): targets for other sizes.** 2560×1440, 3840×2160, the 9:16 1080×1920 preset and fractional frame rates (e.g. 30000/1001) have no row; such a render needs an operator value (`agent_10.render.video_bitrate_bps`, recorded with `target_source = OPERATOR_CONFIG`) or it does not start. INF-12 lists 1440p/2160p values; adopting them is an owner decision.
3. **Codec settings (INF-13):** profile High, `yuv420p`, progressive, CABAC on, `bframes=2`, closed GOP (`open-gop=0`), keyint = half the frame rate (15 at 30 fps; a fractional half such as 12.5 at 25 fps is REQUIRES REVIEW and needs `agent_10.render.gop_frames`), `scenecut=0`, IDR at every segment start (unchanged). No `min-keyint` is passed: x264 clamps it to keyint/2+1 whatever is asked (measured, PR #79 review). `agent_10.render.x264_preset` must be `faster`, `fast`, `medium`, `slow`, `slower` or `veryslow` (never `ultrafast`: Constrained Baseline). `video_encoder` must be `libx264`.
4. **VBV cap: PROPOSAL, REQUIRES REVIEW (Phase 1), on by default (CCR-241).** Each row of `encode_targets.json` carries `maxrate` = 1.5 × and `bufsize` = 2 × the target (12 / 16 Mbps at 1080p 24–30 fps, 18 / 24 Mbps at 48–60 fps). Reason: the measurements of §1 (one-pass ABR bursts to about 4× the target and then starves at every segment start on noisy content; the cap holds each 2 s window within about 1.2× of the target and raised SSIM on the noise clip; it changes nothing on still graphics or ordinary motion). Two-pass was measured as well and did not remove the burst (25.5 then 1.0 Mbps), at about 1.5× the encode time, so it is not used. The ratios are this lane's measured proposal, not a YouTube figure (YouTube: no limit required); the owner or the 3B pilot confirms or changes them. An operator may override both values together (`agent_10.render.video_maxrate_bps`, `.video_bufsize_bps`); the maxrate must be above the target (otherwise x264 switches to CBR).
5. **No edit lists (INF-13, CCR-241).** The final mux uses `-use_editlist 0 -movflags +faststart+negative_cts_offsets` and drops `agent_10.render.aac_priming_samples` (1024, measured; REQUIRES REVIEW on the pinned build) from the start of the master, then cuts the audio to the video length. `qc.video.encoder_settings` fails a file that has an `edts` box in any track.
6. **No filler anywhere.** The argument templates never set `nal-hrd`, `filler` or `-minrate`; QC fails a stream whose SEI shows `filler=1` or `nal_hrd` other than `none`.
7. **`qc.video.encoder_settings` (new, blocking, replaces `qc.video.bitrate`; scope widened by CCR-241).** Measured on the final MP4: `codec_name = h264`, `profile = High`, `pix_fmt = yuv420p`, `field_order = progressive`, `r_frame_rate` = project rate, `has_b_frames ≥ 1`, no edit list, keyframes at frame 0 and at every segment start with no keyframe interval above the GOP (packet flags). Declared: exactly one x264 SEI per render segment, and **every** SEI with `cabac=1`, `bframes=2`, `open_gop=0`, `interlaced=0`, `keyint` = the GOP, `rc=abr`, `bitrate` = target/1000, the configured VBV, no filler. Bound: the render checks each segment file's SEI before the concat (a wrong segment, also a reused or adopted one, is `RESOURCE.RENDER_CRASH`) and records `encoder.settings_sha256` (SHA-256 of the list of the SEI-text hashes); QC recomputes it from the final file and fails a mismatch. **Limit:** the SEI is written by the encoder itself; the target bitrate and the VBV values cannot be measured from the stream (ABR legitimately undershoots on simple frames). A doctored SEI text fails by the binding (and the final file is also bound to the `renders` row by its SHA-256), not by a measurement. Any difference or no SEI = FAIL, remedy `s10_render`. The H.264 level is recorded only (no sourced value: REQUIRES REVIEW).
8. **`qc.video.quality_metric` (new, REPORT ONLY in 3A).** Each segment encode also writes the same filtered frames losslessly (FFV1, Matroska, scratch only, deleted on every path including a failed or stopped encode); the render computes SSIM with both inputs re-timed by frame index (`[0:v]settb=AVTB,setpts=N/FRAME_RATE/TB[a];[1:v]…[b];[a][b]ssim=stats_file=-`), requires the pair count to equal the number of (sampled) frames (otherwise the segment is reported as not measured, never as a wrong value), stores the `All` value and the pair count per segment in the checkpoint, and reports the frame-weighted mean and the lowest segment in `encoder.quality_metric`. VMAF is not computed: the build has no `libvmaf`; the output says `vmaf_status = LIBVMAF_NOT_IN_BUILD` (or `LIBVMAF_IN_BUILD_NOT_USED` on a build that has it; wiring VMAF there is REQUIRES REVIEW). The QC check writes the value into the QC report as a non-blocking `WARN` with `threshold = null` and `details.report_only = true` (18 §7.0.4 convention for an unset threshold; `check_verdict` has no `INFO` value). The threshold key `qc.video.quality_min_ssim` is **unset in 3A**; 3B sets it, and whether it then blocks is also a 3B decision (until then a set threshold still gives only PASS / WARN, never blocking).
9. **FFV1 scratch cost and its bound.** `agent_10.render.quality_sample_every` (default 1 = every frame, exact) keeps only every n-th frame in the reference and in the SSIM; together with the segment length it bounds the scratch size (see §4 for the measured sizes). Decision for 3A: every frame (the development renders are short); the 3B pilot sets n and the segment length for long noisy footage.
10. The measured video bitrate stays in the outputs (`probe.video_bitrate_bps`, QC `measurements.video_bitrate_bps`) as a reported number; it is not a gate.

## 4. Consequences
- Static and graphic content passes with whatever bitrate x264 needs; no padding, smaller uploads.
- Directive §1A.5 "15–25 Mbps at 1080p" is no longer the configured target (D10 sets YouTube's value as the target). **Open question Q-D10-1 (provisional default per owner rule A.9: YouTube's target applies; the 15–25 Mbps band is withdrawn):** the owner confirms that the 15–25 Mbps directive band is replaced, not kept as an upper band.
- CPU, memory and disk (measured by the PR #79 review on a shared 4-CPU box; treat as upper bounds): FFV1 1080p30 3.25 MB/s (testsrc2) to 76.5 MB/s (noise), i.e. up to about 4.6 GB per 60 s segment at 30 fps and about 9 GB at 60 fps; RSS about 600–930 MB with split + FFV1 vs about 290 MB for x264 alone; a 10-minute 1080p30 render about 25 min (testsrc2-like) to 34 min (noise) for encode + reference vs about 8 min for x264 alone, plus 3.5–12.5 min for SSIM. Mitigation: `quality_sample_every` and the segment length (decision 9); a free-space pre-check is not built (REQUIRES REVIEW for the VPS placement). Re-measure on pilot renders (3B) before the VPS night window is used.
- The VBV cap changes the bit distribution only on content that would exceed it; the ratios are a measured proposal (decision 4).
- **Follow-up ticket T-ADR014-1 (other lane, not changed here):** PR #71 `amw_delivery/vertical.py` `make_9x16` encodes with `-crf` and a configurable profile, without the ABR target, B-frames, GOP, CABAC, VBV or no-edit-list rules of this ADR. The 9:16 target itself is REQUIRES REVIEW (decision 2); when it is set, `make_9x16` should use the same `encode.resolve` settings and pass `qc.video.encoder_settings`.
- **Open question Q-D10-2 (provisional default: kept):** the operator value `agent_10.render.video_bitrate_bps` unlocks a size or frame rate without a row (decision 2); D10 did not state this knob (owner rule A.5). Until answered, it is the only way to render 9:16 or 1440p and its source is recorded as `OPERATOR_CONFIG`.
- A segment adopted from storage without a checkpoint, or a replay without segment records, has no SSIM value: the check reports `NOT_MEASURED` (never PASS).
- Contract changes (CCR-240): 18 §6, §7.1, §7.11, §7.12, §12, §13, §14; blueprint 10 §8.1 (`encoder.rate_control`, `encoder.quality_metric`), §20.1 rows 14 and 14a, §21, §24.2, §17; eval cases DC-40…DC-44; the self-test fixture "12 Mbps" becomes the encoder-settings and SSIM fixtures. No GLOSSARY, 03, 04, 07 or 24 change, so no generated code is affected (R-SYNC not triggered).

## 5. Revisit triggers

2. A 1440p, 4K, 9:16 or fractional-rate render is wanted (rows for `encode_targets.json`), or PR #71's 9:16 path is aligned (T-ADR014-1).
3. YouTube changes Help 1722171 (re-verify INF-12 / INF-13 per the 30-day rule).
4. A different encoder (no x264 SEI) is proposed: the settings check needs another evidence source.
5. 3B pilot: the VBV ratios (decision 4), `quality_sample_every` and the segment length on real footage (decision 9).
