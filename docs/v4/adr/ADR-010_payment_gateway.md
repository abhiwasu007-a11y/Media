## 1. Context
- §1C.9 requires usage metering from S4, plans and credits, **invoices with Indian GST**, **a payment gateway adapter chosen in an ADR (Indian gateway first, international later)**, dunning, and plan limits enforced in the queue. Client billing is a platform feature; the owner's own spending still follows rule 8.
- Already fixed by the contracts (this ADR does not change them): `subscriptions.gateway_ref` and `invoices.gateway_ref` exist (04 §5.25, "ADR-010"); `invoices.number` is unique per org and an issued invoice is never edited (a correction is a new document; 14 §3.10, MT-9.3); webhook/callback processing must be **idempotent and signature-checked** and a duplicate must not double-credit (MT-9.4); `subscription_status` is `ACTIVE → PAST_DUE → SUSPENDED → CANCELLED`; suspension holds **new admission** with a stated reason, running jobs finish, and **dunning never deletes data** (20 §11); no LLM computes, rounds or explains an amount (14 §3.10); idempotency scope `billing.charge` keyed on the invoice ID (03 §9.2); a credit or refund is a `SPEND` approval and a price change a `POLICY_CHANGE` approval (14 §3.10).
- `pricing.gateway_fee_rate` is a config variable in the margin formula (21 §6); its value is waiting for this ADR (21, "REQUIRES REVIEW (Phase 1): payment-gateway ADR").
- No card data may touch the platform: a payment gateway holds it (22 §"no payment-card data"). The gateway is a sub-processor and goes on the generated sub-processor list (22).
- Facts below were read from the official vendor pages on 2026-11-18 (HTTP fetch). Where a page could not be read, or was served in a non-India variant, the value is **not** recorded and is marked REQUIRES REVIEW. Vendor facts are ESTIMATE-level inputs until the owner has a quote or an account dashboard (rule 4); none is a commitment.

## 2. Decision
1. **One `PaymentGatewayAdapter` Protocol** in `amw_adapters/payments/`, with a **fake gateway** and recorded fixtures for tests (27 §8: no network, no spend in tests). No vendor name, key, plan ID or URL is hard-coded; the active gateway, its mode (test/live) and its credentials are configuration and secrets (D1, 08 §3). The platform is the **source of truth for plans, usage, invoices and GST**; the gateway only **collects money and reports outcomes**. This keeps a gateway swap (Indian to international, or a second gateway) a new adapter, not a data migration.
2. **Operations the Protocol must offer** (names are descriptive; final method names are set in `SOURCE_LAYOUT.md` when the Tier 2 slice is specified):
   - `create_payment_request(invoice)` returning a hosted payment page or link reference (card data never enters the platform; hosted or redirect checkout only); stored in `invoices.gateway_ref`.
   - `fetch_payment(gateway_ref)` for reconciliation and for the API fetch that vendors recommend when a webhook is late (PG-01).
   - `verify_and_parse_webhook(raw_body, headers) → NormalisedEvent` or a signature failure (see 4).
   - `refund(payment_ref, amount_minor, idempotency_key)` (only after a `SPEND` approval, 14 §3.10).
   - Later (Tier 2, only if the owner wants auto-renewal): `create_mandate` / `charge_mandate` / `cancel_mandate`. Not part of the first adapter release (see 6).
   `NormalisedEvent` is limited to what the platform needs: `PAYMENT_CAPTURED`, `PAYMENT_FAILED`, `REFUND_PROCESSED`, `MANDATE_ACTIVE`, `MANDATE_FAILED`, `SUBSCRIPTION_HALTED_BY_GATEWAY`. This is an adapter-internal type, not a database enum; if it must be stored it needs a CCR (see contract requests).
3. **Candidate order (provisional, owner decides after a written quote and KYC check, never before):**
   | Role | Candidate | Basis (evidence) | Open |
   |---|---|---|---|
   | Indian gateway, first adapter | **Razorpay** | Webhook signature, duplicate and retry rules fully read (PG-01); subscription retry/halt model read (PG-02); one product covers India collection and international cards by request (PG-03). | India fee schedule not read (PG-04) → **REQUIRES REVIEW (Phase 1): Razorpay India fees, KYC and onboarding terms, settlement times** |
   | Indian alternative | **Cashfree** | Subscription and mandate product exists in the docs navigation; headline fee read (PG-05). | Webhook signature/retry docs not read → **REQUIRES REVIEW (Phase 1): Cashfree webhook and subscription behaviour** |
   | International (later) | **Stripe** | Webhook and billing events read (PG-08); India access is invite-based (PG-06); India e-mandate support is public preview (PG-07). | India availability and Billing fees → **REQUIRES REVIEW (Phase 1): Stripe invite status for an Indian business, Billing price, export-of-services settlement** |
   This is a shortlist for a decision, not a configured provider. The first concrete adapter is written only after the owner approves one candidate (rule 8, §1C.15).
4. **Webhook intake (mandatory properties, from MT-9.4 and the vendor facts above):**
   a. The receiving endpoint reads the **raw body**, verifies the vendor signature (HMAC with the webhook secret; both PG-01 and PG-08 require the unparsed body) before any parsing, and rejects with a non-2xx and a security log line on failure. A signature failure is a `PERMANENT.*` outcome and never counts toward a breaker (07 §4: client-side errors never count). A dedicated error code is requested (pending CCR).
   b. **Idempotent:** the gateway's event ID (Razorpay `x-razorpay-event-id`, PG-01; Stripe event ID) is the natural key of a new idempotency scope `billing.webhook` (pending CCR) in `idempotency_keys` (04 §5.9, 03 §9.1 steps). A repeated event returns the stored result and performs nothing: a duplicate never double-credits, never double-marks an invoice `PAID`.
   c. **Fast and durable:** the handler stores the verified event, returns 2xx, and processes asynchronously from the Postgres queue (ADR-001); processing failures retry inside the platform with the `temporary` policy (07 §3), so the vendor's own retry window (24 hours for Razorpay, three days for Stripe: PG-01, PG-08) is never the only safety net.
   d. **Reconciliation job** (scheduled system job, pending CCR): for every `ISSUED` invoice older than a configured age, call `fetch_payment` and settle the difference. A missed or disabled webhook (PG-01: a webhook is disabled after 24 hours of failures) must not leave an invoice stuck.
   e. **Tenant context:** the invoice, found by `gateway_ref` or an `invoice_id` carried in the gateway's notes/metadata field, supplies the `org_id`; the event is processed inside that tenant's transaction (RLS, 04 §3). An event that names no known invoice, or one whose `org_id` disagrees, is a `PERMANENT.TENANT_MISMATCH` security event.
   f. **Network exposure:** the vendor requires ports 80/443 and recommends IP allow-listing (PG-01). Publishing an inbound endpoint on the shared server is a security decision for `08_SECURITY.md` and the deployment ADR: **REQUIRES REVIEW (Phase 1): how the webhook endpoint is exposed without opening the shared server beyond its isolation rules (ADR-012 / 10_DEPLOYMENT_AND_MIGRATION).**
5. **GST invoicing (platform-issued, deterministic; ⚖).**
   - The **platform issues the tax invoice**, not the gateway. Gateway-generated invoices (e.g. Razorpay's automatic cycle invoices, PG-02) are payment records, not the GST document.
   - Amounts are integer paise (`amount_minor`, `tax_minor`, `currency`); GST is added on top of the quoted ex-tax price and never sits inside the margin (21 §6). The calculation is plain code with a test per rule; **no LLM computes, rounds or explains an amount** (14 §3.10).
   - Issued invoices are immutable; `invoices.number` unique per org (04 §5.25, MT-9.3). A correction, refund or write-off is a **credit note, a new document with its own number** (14 §3.10 acceptance 4). The storage shape for a credit note and for the buyer's tax details is not in 04: see contract requests (pending CCR).
   - **Not decided here, all ⚖ and all REQUIRES REVIEW (Phase 1):** owner's GST registration status (A6-b); GST rate and the accounting code of the service; place-of-supply rules between Indian states; treatment of exports to foreign clients (zero-rated or not); required invoice content and numbering series; e-invoicing applicability by turnover; invoice and ledger retention period (04 §7 and 22: "no RESEARCH_LOG entry"); treatment of gateway fees and their GST. Source for each: the GST law/portal pages or the owner's CA. No rate or threshold appears in this repository until read from an official source.
6. **Dunning (maps to the existing four-state enum; no new states).**
   | Platform state | Entered when | Effect |
   |---|---|---|
   | `ACTIVE` | payment captured or period paid | normal admission |
   | `PAST_DUE` | invoice `OVERDUE`, or a `PAYMENT_FAILED` / `SUBSCRIPTION_HALTED_BY_GATEWAY` event | client and owner notified through `notify.send`; running and queued work continue |
   | `SUSPENDED` | grace period elapsed, set by the platform's own scheduled job | **new admission held** with the stated reason (20 §11, MT-2.3); running jobs finish; files remain readable for the grace period set in `22`; **nothing is deleted** |
   | `CANCELLED` | client request, or owner decision after prolonged suspension (`POLICY_CHANGE`-level action by the platform org's `ORG_OWNER`) | offboarding per `22` |
   - Gateway retry behaviour is **input**, not the schedule: Razorpay retries cards on T+1, T+2, T+3 and then halts (PG-02); Stripe attempts an India-issued card once (PG-07). The platform keeps its own schedule, so behaviour is the same on any gateway.
   - **Reminder cadence and grace-period lengths are owner and ⚖ decisions** (20 §13 item 10): they are configuration (key names pending CCR), with no default invented here.
   - A payment returning after `SUSPENDED` moves the subscription to `ACTIVE` and releases the admission hold automatically; it does not re-run held jobs without admission rules (05 §7.1).
   - Automatic card retry or e-mandate charging is **optional** and off in the first release: the first Tier 2 release collects by payment link / hosted checkout on an issued invoice (also the documented choice for variable, usage-based amounts: PG-02). Mandate-based auto-renewal is added only when the owner wants it, because it brings the RBI rules in PG-07 (e-mandate registration, pre-debit notice of at least 24 hours, additional authentication above INR 15,000 each time). **REQUIRES REVIEW (Phase 1): the RBI text itself ⚖** (PG-07 is the vendor's description, not the regulator's).
7. **International later.** The adapter is selected per org by configuration (`billing currency` and customer country decide the route; the exact key is pending CCR). INR via the Indian gateway; foreign-currency collection through the same gateway if its international option is enabled (PG-03) or through a second adapter (Stripe candidate). The platform stores amounts in the currency of the invoice and never converts silently: currency conversion fees (PG-06: +2% where conversion is required) are gateway costs, recorded as a cost, not as revenue. **REQUIRES REVIEW (Phase 1): foreign-exchange and export-of-services compliance for foreign receipts ⚖** (not covered by any recorded fact).
8. **Money-flow safety.** Refunds and credits need a `SPEND` approval (14 §3.10); a plan or price change needs `POLICY_CHANGE`. The adapter's `refund` call uses an idempotency key on scope `billing.charge`-family keys (final scope name pending CCR). No agent may issue a refund unprompted. Gateway keys, webhook secrets and the test-mode credentials are secrets, never in git, logs, or shared variables (08 §3, D1); tenant-held credentials, if clients ever bring their own gateway, are encrypted (08 §3 rule 5) and are out of scope for the first release.
9. **Gateway fee in pricing.** `pricing.gateway_fee_rate` (21 §6, pending CCR-21-3) stays **unset** until the owner has a written fee quote. Figures in §1.1 are labelled as read on 2026-11-18, including Cashfree's promotional rate valid only to 31-Mar-27 for a limited sales volume, and must not be copied into pricing as a rate. Fees are recorded as costs with `figure_kind = ESTIMATE` then `VERIFIED` from the settlement statement (09 §6.4).
10. **Failure handling** follows 07: `TEMPORARY.NETWORK` / `TIMEOUT` / `RATE_LIMITED` / `UPSTREAM_5XX` from an outbound gateway call retry; `PERMANENT.AUTH_INVALID` (credential rejected) fails and escalates to L3 (security/ops); one circuit breaker per gateway (07 §4); a gateway outage never marks an invoice failed; it only delays collection. Stuck `IN_PROGRESS` `billing.*` keys run the reconciliation procedure (03 §9.1) before any new attempt, as for publishing keys.
11. **No spend, no account.** Creating a gateway account, completing KYC, enabling international payments, or any live transaction is the owner's act, after the owner has approved a candidate (rule 8). Tests use the fake gateway and recorded fixtures only; a gateway **test-mode** account (which also needs an account) is a 3C step, only after approval.

## 4. Consequences
- Positive: one interface for any gateway; webhook handling is the same on all of them (raw-body signature, event-ID dedupe, async processing, reconciliation); dunning behaviour is the platform's and does not change with the vendor; no card data enters the platform; invoices and GST are deterministic code under test.
- Negative: the platform must build invoice generation, credit notes and a reconciliation job itself rather than lean on a vendor engine; a public webhook endpoint adds attack surface (08); RBI mandate rules add work if auto-renewal is wanted.
- Contract gaps (see structured list): idempotency scope for inbound webhooks, error code for a failed signature, tax details of a buyer, credit note storage, a persisted inbound-event record, dunning and reconciliation config keys, gateway-selection config key, and the research-log entries PG-01 … PG-08.
- 3A and 3B are unaffected. The only 3A/3B obligation is already in the contracts: money in integer minor units with a currency, `org_id` everywhere.
